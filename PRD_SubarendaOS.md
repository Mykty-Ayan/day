## 1. Краткое описание (TL;DR)

SubarendaOS — это операционная система для независимых субарендаторов, которые сдают квартиры **по часам и посуточно**. Продукт закрывает три ежедневные боли оператора: наложение броней, непонимание реальной прибыли по каждой квартире и хаос в обороте (уборка/доступ/расходники).

Ключевое отличие от существующих PMS (Bnovo, Realtycalendar, TravelLine) — поддержка **почасовых слотов внутри дня** с буфером на уборку, тогда как рыночные решения заточены под ночёвки.

Продукт мультитенантный: каждый оператор работает в изолированном пространстве и **не видит данные других**. Центральной консолидации выручки нет — операторы независимы, деньги и реклама у каждого свои.

---

## 2. Проблема

Субарендатор, ведущий несколько квартир по часам, сегодня работает «на коленке» — в заметках телефона, тетради и голове. Из этого вытекает:

- **Двойные брони.** Почасовая сдача = высокая оборачиваемость (5–10 заездов в день на квартиру). Ручной учёт слотов приводит к накладкам и конфликтам с гостями.
- **Слепота по деньгам.** Оператор не знает, какая квартира зарабатывает, а какая работает в минус после вычета аренды собственнику, уборки, коммуналки, стирки и рекламы.
- **Провалы в обороте.** Уборщица не знает, когда убирать; бельё и расходники заканчиваются некстати; коды доступа путаются.
- **Реклама как чёрная дыра.** Деньги на пакеты Krisha тратятся, но связь «затраты → брони → окупаемость» никто не считает.
- **Нет памяти о гостях.** Проблемные гости возвращаются, потому что нет чёрного списка; постоянных гостей не удерживают.

## 3. Целевая аудитория

**Основной пользователь — независимый субарендатор** (оператор), который:
- Арендует 1–6 квартир и пересдаёт их по часам/суткам;
- Ведёт бизнес сам или с 1–2 помощниками (уборщица, диспетчер);
- Работает в KZ-контексте: оплата через Kaspi, реклама на Krisha, доступ через кодовые замки/кейбоксы;
- Сам отвечает за свои финансы и рекламу — центральной структуры над ним нет.

**Сегменты по масштабу:**

| Сегмент | Кол-во квартир | Главная боль |
|---|---|---|
| Новичок | 1 | Порядок в бронях и понимание, выгодно ли вообще |
| Растущий | 2–4 | P&L по каждой квартире, оборот, чёрный список |
| Профи | 5+ | Персонал, аналитика загрузки, оптимизация рекламы |

**Кто НЕ является пользователем:** собственники квартир, гости, агрегаторы/сети с единой кассой. (Взаиморасчёты «центр ↔ оператор» — вне продукта, т.к. операторы независимы.)

## 4. Цели и не-цели

**Цели (что решаем):**
- G1. Исключить двойные брони через почасовый календарь.
- G2. Дать оператору честную прибыль по каждой квартире в реальном времени.
- G3. Упорядочить оборот: уборка, доступ, расходники.
- G4. Сделать рекламные траты измеримыми (стоимость брони, окупаемость).
- G5. Обеспечить строгую изоляцию данных между операторами.

**Не-цели (что осознанно НЕ делаем в этой версии):**
- N1. Не строим канал-менеджер / синхронизацию с Booking, Airbnb, Krisha по API (Krisha не даёт публичного booking-API; брони заводятся вручную).
- N2. Не делаем онлайн-приём платежей внутри продукта (оплата остаётся в Kaspi; мы только фиксируем факт).
- N3. Не делаем консолидацию/взаиморасчёты между операторами.
- N4. Не делаем публичный сайт бронирования для гостей.
- N5. Не делаем бухгалтерию/налоговую отчётность (только управленческий учёт).

## 5. Успех продукта (метрики)

| Метрика | Что показывает | Целевой ориентир (пилот) |
|---|---|---|
| Activation | Оператор завёл ≥3 брони и ≥1 расход в первую неделю | ≥ 2 из 3 пилотных операторов |
| Retention | Оператор ведёт учёт на 4-й неделе | ≥ 2 из 3 |
| Data completeness | Доля броней с заполненной ценой и источником | > 80% |
| Ноль накладок | Двойные брони после внедрения | 0 |
| Time-to-value | Время от старта до первого готового P&L | < 30 минут |

Северная звезда: **число квартир, по которым оператор ведёт полный учёт еженедельно.**

## 6. Объём и фазирование

Продукт выкатывается в две фазы. Это осознанное решение: строить мультитенантный SaaS до валидации спроса — значит месяцы разработки под гипотезу.

### Фаза 1 — MVP: трекер для одного оператора (пилот)
Формат: **шаблон-таблица** (Excel / Google Sheets), по копии каждому из 3 операторов. Отдельные файлы = изоляция бесплатно, без серверов и логинов. Цель — проверить, что операторы вообще ведут учёт, и отточить модель данных на живых данных.

Входит: Объекты, Календарь броней (почасовой), Финансы + P&L, Учёт рекламных трат, базовая аналитика.

### Фаза 2 — V1: веб-приложение с аккаунтами
Проверенный шаблон превращается в мультитенантное приложение: вход для каждого оператора, изоляция на уровне БД, роли (оператор / помощник), уведомления. К этому моменту шаблон уже служит готовым ТЗ.

Добавляется: Роли и доступ, Уборка/оборот как задачи, CRM гостей с чёрным списком, Расходники, расширенная аналитика, уведомления.

## 7. Функциональные требования

Ниже — модули с требованиями. Приоритет: **P0** = MVP (Фаза 1), **P1** = V1 (Фаза 2), **P2** = позже.

### 7.1. Объекты (квартиры) — P0
- FR-1. Создание карточки квартиры: название, адрес/ЖК, кол-во комнат, площадь.
- FR-2. Условия аренды у собственника: ежемесячный платёж, дата платежа, депозит, отметка «есть письменное согласие на субаренду» (юр. риск).
- FR-3. Способ доступа: кодовый замок / кейбокс / ключи; поле для текущего кода.
- FR-4. Тарифная сетка по времени суток (день / вечер / ночь / сутки) — как у конкурентов на Krisha.
- FR-5. Оснащение и фото (для V1).

### 7.2. Календарь и брони (ядро) — P0
- FR-6. Бронь с точностью до **часа**: квартира, дата, время заезда/выезда, длительность.
- FR-7. **Защита от наложений** — система не даёт создать бронь на занятый слот той же квартиры. Ключевое требование продукта.
- FR-8. **Буфер на уборку** между бронями (настраиваемый, напр. 30–60 мин); слот буфера считается занятым.
- FR-9. Атрибуты брони: цена, предоплата (сумма + факт получения), источник (Krisha / Instagram / 2GIS / повторный / рекомендация), гость (телефон/имя), комментарий.
- FR-10. Статусы: запрос → подтверждён → заселён → выехал → отмена / no-show.
- FR-11. Визуальный календарь: день/неделя, по квартирам; занятые/свободные слоты видны с одного взгляда.
- FR-12. Отметка способа оплаты (Kaspi / наличные) — для сверки кассы.

### 7.3. Финансы и P&L — P0
- FR-13. Доход автоматически собирается из подтверждённых/завершённых броней.
- FR-14. Расходы по категориям: аренда собственнику, коммуналка, уборка, стирка, расходники, реклама, ремонт/замена, прочее — с привязкой к квартире.
- FR-15. **P&L по каждой квартире** (доход − прямые расходы) за период; итог по оператору.
- FR-16. Касса/долги: кто должен предоплату, сколько наличных на руках.
- FR-17. Отчёт за период (неделя / месяц) с разбивкой по квартирам.

### 7.4. Реклама и окупаемость — P0 (базово) / P1 (полно)
- FR-18. Учёт трат на продвижение Krisha по каждой квартире (пакеты ×5/×15, ТОП/Горячие на сутки — см. модель услуг Krisha).
- FR-19. Связка «источник брони = Krisha» → расчёт **стоимости брони** и **окупаемости (ROI)** по квартире и по каналу.
- FR-20. Напоминание о продлении рекламы / истечении 14-дневной актуальности объявления (P1).

### 7.5. Уборка и оборот — P1
- FR-21. Автоматическая задача на уборку после выезда гостя (в буфер-слот).
- FR-22. Назначение уборщицы, чек-лист (бельё, полотенца, расходники), отметка «выполнено».
- FR-23. Стыковка расписания уборки с бронями (нельзя заселить до уборки).

### 7.6. Гости / CRM — P1
- FR-24. База гостей: телефон, имя, история броней, источник.
- FR-25. **Чёрный список** проблемных гостей с причиной; предупреждение при попытке брони.
- FR-26. Метка постоянных гостей; депозиты.

### 7.7. Расходники и инвентарь — P1
- FR-27. Остатки по квартире (бельё, полотенца, туалетные принадлежности, вода/кофе) и точка дозаказа.
- FR-28. Списание при обороте, напоминание о пополнении.

### 7.8. Роли и доступ (мультитенантность) — P1
- FR-29. Регистрация/вход оператора; **полная изоляция данных** — оператор видит только свои квартиры и брони.
- FR-30. Роль «помощник» (уборщица/диспетчер) с ограниченными правами внутри одного оператора.
- FR-31. Роль «владелец продукта» (вы): управление операторами, подписками; **без доступа к операционным цифрам операторов** (или только по явному согласию) — иначе теряется доверие.

### 7.9. Аналитика — P1/P2
- FR-32. Загрузка квартиры (occupancy), выручка на квартиру, средний чек, средняя длительность брони.
- FR-33. Загрузка по часам и дням недели → подсказка, когда усиливать рекламу (стыкуется с рекламной стратегией на Krisha).
- FR-34. Сравнение эффективности квартир между собой (внутри одного оператора).

### 7.10. Уведомления — P1/P2
- FR-35. Напоминания: скоро заезд, пора убирать, платёж собственнику, продление рекламы.
- FR-36. Каналы: push / WhatsApp / Telegram (уточнить на этапе V1).

## 8. Нефункциональные требования

- NFR-1. **Изоляция и безопасность.** Строгое разделение данных между операторами на уровне БД; утечка чужих данных — критический дефект.
- NFR-2. **Мобильность.** Оператор работает с телефона на ходу — mobile-first интерфейс обязателен.
- NFR-3. **Язык.** Русский и казахский интерфейс; валюта — тенге.
- NFR-4. **Локальный контекст.** Kaspi как способ оплаты, Krisha как канал, кодовые замки как доступ — учтены как первоклассные сущности, а не «прочее».
- NFR-5. **Скорость ввода.** Создание брони — не более чем в 3–4 тапа; это то, что оператор делает десятки раз в день.
- NFR-6. **Оффлайн-устойчивость (P2).** Ввод брони без сети с последующей синхронизацией.

## 9. Модель данных (ключевые сущности)

```
Оператор (tenant)
 └── Квартира
      ├── ТарифнаяСетка (по времени суток)
      ├── Бронь ──── Гость
      │     ├── Оплата (Kaspi/нал, предоплата)
      │     └── ЗадачаУборки
      ├── Расход (категория, сумма, дата)
      └── РекламнаяКампания (Krisha, траты, период)
Гость ──── ЧёрныйСписок (флаг + причина)
Помощник ──(принадлежит)── Оператор
```

Границы изоляции проходят по сущности **Оператор**: любой запрос данных всегда отфильтрован по текущему оператору.

## 10. Ключевые продуктовые решения и обоснования

- **Почему почасовые слоты, а не ночёвки.** Это единственная реальная дыра в существующих PMS и главная причина, по которой субарендаторы ведут учёт вручную. Здесь наша дифференциация.
- **Почему сначала таблица, а не приложение.** Валидация спроса за дни, а не месяцы. Если 3 оператора реально ведут учёт в шаблоне — есть продукт; если забросили — сэкономили разработку.
- **Почему нет консолидации и взаиморасчётов.** Операторы независимы (подтверждено); это упрощает продукт до «одиночного трекера × изоляция».
- **Почему брони заводятся вручную.** У Krisha нет публичного booking-API, гости пишут/звонят напрямую — автоввод невозможен, и это нормально для сегмента.

## 11. Монетизация (на проработку)

Поскольку операторы независимы и рекламу ведут сами, продукт для них — чистое удобство учёта. Кандидаты:
- Подписка на оператора (фикс/мес);
- Плата за количество квартир (напр. до 3 бесплатно, дальше платно);
- Freemium: MVP-функции бесплатно, аналитика/уведомления/персонал — платно.

Модель монетизации напрямую влияет на то, **когда** вкладываться в Фазу 2: без готовности платить — веб-приложение преждевременно.

## 12. Риски и допущения

| Риск / допущение | Влияние | Как снижаем |
|---|---|---|
| Операторы не захотят вести учёт (привычка к «тетради») | Высокое | Пилот на таблице до вложений в код |
| Юр. риск субаренды без согласия собственника | Среднее | Поле-напоминание в карточке, дисклеймер; не блокируем |
| Почасовой UI сложнее ночного календаря | Среднее | Прототип и тест на реальных операторах в Фазе 1 |
| Изоляция данных нарушена в V1 | Высокое | Изоляция как требование №1 в архитектуре, тесты доступа |
| Малый рынок (нишевый сегмент) | Среднее | Начать с 3 операторов, расширять по сарафану |
